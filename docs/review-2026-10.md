# Code review, October 2026

A whole-codebase review of kikitori at `4b353a0`: capture, both pipelines, the read-ahead
(Sync), speaker labels, the Claude clients, storage, the app model, views, the injected page
scripts, the CLI and the tests. Not a diff review: every file was treated as unreviewed.

## How it was done

1. **Map.** README, `docs/design/` (spec, realtime-sync, speaker-labels), then the data flow
   from capture to screen: tap or page audio → `metered` → `LivePipeline` (chunker → recognizer
   → translator, plus live line and speakers) → `AppModel.handle` → views and overlay; and for
   the built-in player, `MediaTapScript` → `kkMedia` → `MediaPipeline` (`Cutter` →
   recognizer → translator) → `PlayerController.addCues` → `PlayerScript` reveal → `kkReveal`
   → transcript.
2. **Five independent passes**, each in a fresh context: synced path correctness; live path
   and speaker labels; Swift concurrency; resources and performance; error handling, security
   and AI-code smells (SDK calls were checked against the macOS 26 SDK's `.swiftinterface`
   files and FluidAudio's source, not memory). Two passes found the top issue (Pause/Stop)
   independently.
3. **Proof before fixing.** Each finding below has a failing test (now a regression test), a
   probe, a measurement or a precise trace. Findings that didn't hold up were dropped (end of
   this report).
4. **Adversarial check.** A separate reviewer tried to refute every fix and find regressions
   (section "Adversarial check").
5. **Verification.** `swift build` with no warnings; `swift test` 94 tests passing (84 before,
   10 new); snapshots rendered; `kk-check-reveal` passes; a real `--player-test` run (below).

## Findings, most severe first

Severity is impact on the user times likelihood. "Test" means a regression test now in
`Tests/`, which failed before its fix and passes after.

### 1. Synced subtitles: speech cut at every append after a seek back — High

`MediaPipeline.swift`, `Cutter.step`. When a run reached the end of the audio decoded so far,
it was treated as a gap if *any* audio existed further on, even far beyond the 30 s horizon
(left from before a seek back, kept 5 minutes). Each 0.5 s append was then flushed as its own
chunk: speech split mid-word into ~0.5 s fragments, each recognized and sent to Claude (up to
~10× the requests).
- **Evidence:** test `speechOverTheBufferedEdgeIsOneChunk(audioFarAhead: true)`: speech 18.5–21.5 s
  came out as 4 chunks with audio at 100 s, 1 chunk without.
- **Fix:** only audio within the horizon makes a gap (`bf5d742`).

### 2. Pause and Stop didn't end the run — Medium

`AppModel` (`pipelineTask`, `mediaTask`), every stage of `LivePipeline` and `MediaPipeline`.
Cancelling a task iterating an `AsyncStream` still hands out everything already buffered.
- Events queued for the main actor were handled after Pause: a `.heard` re-added lines to
  `pendingLines` after `stopCapture` cleared them, so they showed "translating" dots for the whole
  pause and Explain Last Line skipped them. A stale `.hearing` came back.
- On a source switch (`stop(); start()`), leftover events landed in the *new* session: a
  line from the previous source with the old clock, and its translation cost.
- Every cancelled stage kept working through its backlog (recognition, diarizer, translation)
  beside the next run.
- **Evidence:** test `aStoppedPipelineDoesNotWorkThroughItsBacklog`: with 20 chunks queued, 17
  were recognized after the stop (now ≤ 1). The concurrency pass reproduced the stale
  `.heard` with a mirror of `AppModel.handle` (`handled after stop: ["heard(time: 0."]`).
- **Fix:** each stage loop stops when cancelled; both app loops handle nothing more once
  cancelled, except bills (a translation or billed failure that came back after its run ended)
  (`3afb2d1`, `03fbd70`).
- **Trade-off:** a Japanese line queued in the instant of a Pause is now dropped rather than kept
  without English (the window is the main actor's queue: milliseconds).

### 3. Synced read-ahead stalled at a gap — Medium

`Cutter.step`. A run starting at a playhead off the 16 kHz grid (any real `currentTime`) could
end a fraction of a sample short of a range end; `samples(from:to:)` then returned nothing
forever and the gap branch never fired. Audio after the gap waited for the playhead itself:
the 30 s read-ahead fell to a few seconds, and late cues aren't drawn on the video.
- **Evidence:** test `aGapIsCrossedWhateverThePlayheadsSubSampleOffset(100.00004)`: 2 of 4
  chunks (100.00001 worked).
- **Fix:** a read that reaches the range end puts the cursor exactly there (`bf5d742`).

### 4. Synced: chunks dropped as stale were lost for good — Medium

The cutter marked a stretch done when it emitted the chunk. If the recognizer later dropped
it as stale (a seek forward > 30 s while chunks were queued), seeking back never gave that
speech subtitles.
- **Evidence:** test `chunksDroppedByASeekAreRedoneOnSeekingBack`: speech at 10–26 s never got
  cues.
- **Fix:** the recognizer reports dropped chunks back through `Playhead`; the cutter un-marks
  them (`Intervals.remove`) (`bf5d742`).

### 5. Synced: the 60 s cue cleanup forgot cues with work still coming — Medium

`AppModel.playerState`. Cues ending 60 s before the playhead were removed with their released
lines, while the page keeps cues up to 30 min.
- A translation in flight across a seek of more than 60 s found no cue: billed, and its line
  stayed "translating" until Stop.
- Seeking back over a skipped stretch: the page revealed cues the app no longer had, so those
  lines never reached the transcript (and are never made again).
- **Evidence:** trace (app target, no tests).
- **Fix:** only the cue *audio* goes after 60 s; cues go after 30 min, settled (`8d92df1`).

### 6. Any iframe could post to the player's message handlers — Medium (security)

`PlayerController`. The handlers are registered for every frame in the page's content world.
An ad or embed iframe could post a `kkState` title (word for word into Claude's *system* prompt,
uncapped: a 200k-character title with "IMPORTANT NEW RULE…" went straight through, and each
change forces a prompt-cache rewrite), `kkMedia` audio that was transcribed and translated, or
`.public` log lines.
- **Evidence:** a WKWebView probe: a `data:` iframe's fake title was accepted, with
  `frameInfo.isMainFrame == false`.
- **Fix:** messages from other frames are ignored; title and channel capped at 200/100
  characters (`27e7d9c`).

### 7. A damaged store file was wiped by the next save — Medium

`AppModel.load/save`, `SessionStore.summaries`.
- An unreadable `profiles.json` loaded as `[]` and the next save erased every profile.
- An unreadable `usage.json` loaded as $0 spent: the monthly cap stopped working, then the
  history was overwritten.
- An unreadable `index.json` made the next save write an index of one session; the others
  vanished from the list, out of reach of retention and Delete All.
- Write failures were silent.
- **Evidence:** test `aDamagedIndexLosesNoSessions`; the errors pass's probe tests for the rest.
- **Fix:** an unreadable file is moved aside (`name.unreadable-<time>.json`) and logged; the
  index is rebuilt from the session files; write failures are logged (`201f8cf`).

### 8. A timeout was reported as offline; Explain timed out early and lost cost — Medium

`ClaudeClient`, `Explainer`, `AppModel.explain`.
- `URLError.timedOut` mapped to `.offline`: "You're offline." / "Offline · Japanese only" with
  the network fine.
- Explain (Sonnet, adaptive thinking, up to 8192 tokens, not streamed) had the same 60 s
  timeout as a live line.
- An Explain cancelled by another checked cancellation before recording its billed cost.
- **Evidence:** test `aTimeoutIsNotOffline`; probe tests in the errors pass.
- **Fix:** a `.timedOut` failure (counts toward "Claude isn't responding" like a 5xx); Explain
  waits up to 150 s; cost recorded before the cancellation check (`ac51cf8`).

### 9. Built-in player: unsynced line times early by the tap's start-up delay — Medium

`AppModel.startCapture`. The line clock's offset was taken when capture was installed, but the
player's `DeferredTapCapture` delivers nothing until the page first plays sound. Start
Subtitles, then a video 40 s later: every line 40 s early in the transcript and exports, and
out of order with synced lines.
- **Evidence:** trace.
- **Fix:** the offset comes from the run's first buffer (`a0f52ac`).

### 10. Live search filtered the whole transcript twice per update — Medium (performance)

`LiveView.shown`. With a search open, every body update (each heard, translated or revealed
line, each keystroke) ran `localizedCaseInsensitiveContains` on four fields of every line,
twice.
- **Before:** 14.6 ms per pass at 5,000 lines (a 3-hour stream), ~29 ms per update (release
  build); 55 ms per transcript event in the perf pass's SwiftUI copy of the view.
- **After:** matching runs detached after a 150 ms pause; the body filters by id: under 1 ms
  (0.5 ms debug, 0.006 ms release) (`13e8545`).

### 11. Two speaker-model downloads at once — Medium

`SpeakerTracker.load`. A player session starts two trackers, each downloading the same
Sortformer files into the same place; FluidAudio's `FileDownloader` resumes and clears
`<file>.partial` with no lock, and a clash makes it delete its cache and fail: labels off for
the session. Each Stop and Start during the first ~230 MB download added another.
- **Evidence:** trace through FluidAudio `Shared/Download/FileDownloader.swift`; not run (needs
  a cold 230 MB download).
- **Fix:** loads take turns (`Gate`), later ones find the files cached; test
  `modelLoadsTakeTurns` (`f959d63`).

### 12. Speaker labels: frames from before a pause stood in after it — Medium-low

`SpeakerTracker.frames` with `LivePipeline`. The tracker lasts the session; each run's clock
restarts at 0. Where the new run had no frames yet (a 0.5 s wait timed out, or muted audio),
the old run's frames for the same times were used: invented speaker turns.
- **Evidence:** test `afterAPauseTheRunBeforeItNeverStandsInForTheNewOne` (was `["B","A"]`
  where only B spoke).
- **Fix:** `ShiftedSpeakerTracker` puts each run on the session clock (`a0f52ac`).

### 13. Synced reveal scanned every cue every frame; old videos' cues never went — Low-medium

`PlayerScript.frame/postReveals`.
- **Before:** 0.46 ms per frame at 2,000 cues (node), ~3 % of a core at 60 Hz, ~5 % at 120 Hz,
  growing through a stream. Cues of a previous video, track or MediaSource were never pruned
  (the prune compared them against the new video's clock).
- **After:** each frame starts at the last minute's cues (binary search) and stops at the
  playhead: 0.004 ms at any count. Cues of another key are dropped when the key changes. The
  500 ms check still scans everything (`c6c4196`).
- **Verified:** `kk-check-reveal` passes; `--player-test` below.

### 14. Recognition failures were invisible — Low-medium

`LivePipeline`/`MediaPipeline`: `try?` turned every recognizer error into empty text. An
engine that always throws gave a session showing "Listening" with nothing, and no trace.
- **Fix:** failures are logged (category `pipeline`) (`d0f9539`). Not surfaced in the UI: see
  "Open".

### 15. Data races between the audio task and the main actor — Low

- `AppModel.lastSoundAt`, `muteInput`, `muteForSync` were `nonisolated(unsafe)` vars, written on
  the main actor and read or written by the detached `metered` task for every buffer.
- `DeferredTapCapture.tap` was set by its polling task and read by `stop()` on the main actor:
  a Stop while the tap was starting left it to a `deinit` that could run on the audio thread.
- **Evidence:** thread-by-line traces (TSan reports nothing because the app target has no
  tests).
- **Fix:** a lock and atomics; the tap is stopped by whichever side comes second (`82cd0e7`).

### 16. A translated line without Japanese got the whole chunk — Low

`LivePipeline` translate stage, with speakers on: an empty `ja` from the translator fell back
to the whole chunk, repeating the other speaker's words.
- **Evidence/fix:** test `aTranslatedLineWithoutJapaneseGetsItsOwnCharacters` (was
  `["あいうえお", "あいうえおかきくけこ"]`); the line gets its own characters (`d0f9539`).

### 17. A superseded start could tear down the newer session — Low

`AppModel.start/startCapture`: the "superseded" check ran only after the awaits succeeded. A
stopped start that then failed (model load, mic permission) stopped the newer session's
capture and dropped its record.
- **Evidence:** trace.
- **Fix:** after each await, a newer decision wins (`55365b0`).

### 18. Small holes in the page audio shifted everything after them — Low

`MediaResampler` placed audio by sample count across holes under 30 ms: 20 lost-frame holes
put a click 0.40 s early.
- **Evidence/fix:** test `smallHolesDoNotShiftLaterAudio`; it follows the packets' times
  (`bf5d742`). How often YouTube streams have such holes is unmeasured.

### 19. Smaller defects, fixed

- **Delete All** removed the profiles but left their voice samples (raw audio) on disk (`55365b0`).
- **API key:** Onboarding and Settings reported a key as saved when the Keychain refused it,
  and Remove reported success when it failed (`be0f09e`).
- **Usage:** the ledger saves 2 s after a change; quitting within that time lost the spend the
  cap counts. Stop and quit save it at once. Explain entries counted input and output tokens
  only, live entries every billed token (`d26ab69`).

## Adversarial check

A separate reviewer tried to refute each of the 15 fix commits and to break them. It ran every
new test against the parent commit's sources: all fail there, so they test the defect, not the
new code. Verdicts: 10 confirmed, 5 plausible (fix sound, defect smaller than claimed:
`ac51cf8`'s cancelled-Explain billing, `be0f09e`, `82cd0e7`, `13e8545`, `c6c4196`), none refuted,
no regressions. It checked in particular that the CLI and tests still drain every event to the
end of a file, that a gap just beyond the horizon is still crossed later, that the reveal
window misses no `kkReveal` (the longest chunk setting is 15 s), that a fresh install and short
empty sessions behave with the index rebuild, and that `cueAudio` doesn't leak.

What it found was fixed (`03fbd70`): late bills behind another queued event weren't counted, a
late bill just before quit wasn't saved, and Settings could show a key as present after a failed
replace. Residual gaps it found are listed under "Not fixed".

## Open: needs a decision

- **"Remember This Voice" writes audio to disk.** `AppModel.saveVoice` keeps up to 15 s of a
  speaker's voice as raw PCM in `voices/<profile>.f32` for the experimental cross-session voice
  memory. The README ("Audio is never saved"), `SessionRecord`'s doc comment and the
  `NSAudioCaptureUsageDescription` ("never saved") say otherwise. It is opt-in and per profile,
  so this is a product decision, not a defect fix: either reword the README and the permission
  text, or keep only the speaker embedding instead of the audio, or drop the feature (design
  note §9 already lists it as open). Left as is.

## Not fixed, with reasons

- **Residuals of the synced fixes** (found by the adversarial check; not regressions, same as
  before):
  - A hole *inside* the horizon that is still filling (rare: a seek back to just before audio
    already decoded) still counts as a gap at each append, so speech over it is split. Fixing it
    means waiting in holes, against the "never wait in a hole" rule the pipeline tests encode.
  - A chunk dropped as stale while the run goes on (the recognizer more than 30 s behind with no
    seek) is marked done again when the run finishes, so seeking back there gives no cue.
  - With speakers on, a translated line without Japanese gets characters split by English
    length, which can overlap the previous line's Japanese (still far better than the whole chunk).
- **A network that stops answering** (timeouts rather than "no internet") now shows "Claude isn't
  responding" after 3 timeouts instead of "Offline" at once.
- **Model loads** waiting their turn ignore cancellation: a hung download delays later loads
  until URLSession gives up.

- **Allocation on the real-time audio thread.** `ProcessTapCapture.handle` runs on the HAL's
  IO thread (the IO block is dispatched synchronously) and allocates buffers, runs
  `AVAudioConverter` and yields to a locking stream there. Under load this can overrun and drop
  input. No overload was reproduced; a fix needs a lock-free ring buffer and a converter
  thread, which is more than a local change.
- **The session is re-saved on the main thread every 30 s:** ~10 ms at 5,000 lines (a 1.2 MB
  JSON), one dropped frame per 30 s. Moving it off the main actor needs ordering with
  `stop()`'s save; not worth the risk for the size.
- **Prompt injection through the video title, channel, profile and glossary.** These are
  trusted context in the system prompt by design. The frame check and caps (finding 6) remove
  the untrusted-iframe route and the cost blow-up; a creator can still title a video to steer
  the subtitles, which affects only that viewer's subtitles. Output is schema-constrained.
- **No retries or backoff.** `retryAfter` is parsed but unused; a rate-limited chunk stays
  Japanese only. After a 401 every chunk still sends a request with the dead key (not billed).
  Behaviour, not a defect; noted for the design.
- **Recognition failures** are logged but not shown (finding 14). Raising an issue after
  repeated failures is a UI decision.
- **Capture-start errors** other than a model failure all show as "Audio access was turned off".
- **`Issue.fallingBehind`** ("Skipped ahead to live") is never raised: dead code from the spec.
- **A 200 answer that fails to decode** loses its cost (rare).
- **Video ids are logged as `.public`** (`sync` and the page's `kkLog`). They help debugging
  the read-ahead; the unified log is local.
- **FluidAudio downloads models from Hugging Face `main`, unpinned** (only `.diarizer` has a
  revision). Upstream's choice.
- **Weak tests:** `PricingTests` re-derive `pricing.json`'s constants;
  `trimsOldestTurnsPastTheBudget` only asserts `count < 11`.

## Dropped (didn't survive checking)

- `KeyCheck` treating 400/404 as a valid key: authentication happens before validation, so a
  400 or 404 means the key was accepted.
- `MainActor.assumeIsolated` from non-main threads: every site is reached on main (WebKit
  messages, main-queue observers, timers, Carbon hotkeys, the `AVAudioPlayer` delegate, checked
  empirically).
- Unbounded memory: replay clips (60 MiB), kept media audio (300 s), page buffers (8 MiB per
  stream), tracker frames and audio, translator history and the ledger are all capped; the
  queues between stages drain faster than real time (recognizer ~1.7 %, diarizer ~3.8 % of real
  time).
- The 8-iteration cap in `Cutter.step` stranding work: a playhead input arrives every 500 ms.
- `MediaTimeline` add/trim, `Intervals`, `CueAligner` (fuzzed), the WebM/MP4 demuxers and the
  JS↔Swift message formats.

## Verification

- `swift build --build-tests`: no warnings. `swift test`: 94 tests in 22 suites pass (84 before).
- `swift run Kikitori --snapshots`: every screen renders as before.
- `swift run kk-check-reveal`: all checks pass.
- A real run, after all fixes: `scripts/bundle.sh debug`, then
  `--player-test "https://www.youtube.com/watch?v=kLFsqvruEFs&t=600s" 90 <log> --muted`
  (translation off, the default). Before-numbers are §11 of `realtime-sync.md`.

  | | Before (design doc) | After |
  |---|---|---|
  | Synced after start | 16 s | 6 s |
  | Reveal error, median / p95 / max | 8 / 16 / 39 ms (284 chars) | 8 / 16 / 36 ms (183 chars) |
  | Cue lead, median (min) | 21.2 s (0.0 s) | 23.8 s (0.1 s), 24 cues |
  | Lines in the transcript / pending at any time | 16 / – | 18 / 0 |
  | Errors, dropped chunks, untranslated-as-stale in the log | – | none |

  The decoded audio stayed ahead of the playhead throughout (17 s growing to 109 s).
